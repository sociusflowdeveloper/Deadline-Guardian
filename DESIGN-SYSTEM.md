# Design system — local package and documentation

**Prepared:** 9 November 2026 (Asia/Singapore). **Organisation:** SociusFlow Pte. Ltd. **Status:** engineering documentation draft for review. Requirements below do not establish implementation, production readiness or legal approval.

## Current surface

CONFIRMED: no browser application or component library is in this repository. Its user surfaces are CLI help/errors, JSON outputs, draft CSV/Markdown reports and host-rendered skill instructions. Do not invent a web palette/components or claim control over the host UI.

## Consistent information design

Use British English, descriptive headings and explicit draft/review labels. Preserve canonical JSON field names and exact evidence strings. Keep ADDED/CHANGED/UNCHANGED/CONFLICT/UNVERIFIED/cancellation meanings aligned with CONTRACT.md. Do not imply certainty through colour or conceal unresolved evidence.

Reports should make previous value, candidate value, source reference and review state easy to compare. All exports remain drafts, with no confirmed changes. Escaping and formula neutralisation are security requirements, not cosmetic options. Fixed safe CLI errors must not disclose content or filenames.

Formal rendered documents should use Times New Roman/serif with readable professional hierarchy; Markdown inherits its renderer, so no font is guaranteed here. Target brand preference is restrained sharp institutional design, without pills or arbitrary decorative colours, if a separate authorised UI is later introduced.

## Accessibility and validation

Use meaningful text headings, explicit status labels and readable table headers. Avoid colour-only meaning. Test actual supported host/report rendering, long excerpts, escaped markup and copy/export behaviour before visual/accessibility claims. Future web components need their own approved design tokens, keyboard/focus/mobile/reduced-motion evidence and rights-cleared assets.
